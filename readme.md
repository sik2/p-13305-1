## 1차 요구사항 구현
- [x] 유저가 루트 url로 접속시에 게시글 리스트 페이지(http://주소:포트/article/list)가 나온다.
- [x] 리스트 페이지에서는 등록 버튼이 있고 버튼을 누르면 http://주소:포트/article/create 경로로 이동하고 등록 폼이 나온다.
- [x] 게시글 등록을 하면 http://주소:포트/article/create로 POST 요청을 보내어 DB에 해당 내용을 저장한다.
- [x] 게시글 등록이 되면 해당 게시글 리스트 페이지로 리다이렉트 된다. 페이지 URL 은 http://주소:포트/article/list 이다.
- [x] 리스트 페이지에서 해당 게시글을 클릭하면 상세페이지로 이동한다. 해당 경로는 http://주소:포트/article/detail/{id} 가 된다.
- [x] 게시글 상세 페이지에는 id에 맞는 게시글 데이터와 목록 버튼이 있다. 목록 버튼을 누르면 게시글 리스트 페이지로 이동하게 된다.

## 미비사항 or 막힌 부분
- 현재 기능은 게시글 목록/등록/상세 조회 중심이며, 수정/삭제 기능은 미구현 상태이다.
- 데이터가 많아질 때를 대비한 검색, 정렬, 페이징 기능이 없어 확장성 보완이 필요하다.
- 로그인/권한 기능이 없어 게시글 등록 및 조회 접근 제어를 적용하지 못한 상태이다.
- 예외 상황에서 사용자 친화적인 안내 페이지와 메시지 처리를 추가로 개선할 계획이다.
- 설정이 `application.yml` 중심으로 구성되어 있어 운영/개발 환경 분리와 민감정보 관리 강화가 필요하다.

## MVC 패턴
- Model: `Article` 엔티티와 `ArticleRepository`가 데이터 저장/조회 역할을 담당한다.
- View: `article_list.html`, `article_form.html`, `article_detail.html`이 사용자 화면을 렌더링한다.
- Controller: `ArticleController`, `MainController`가 URL 요청을 처리하고 적절한 화면으로 연결한다.
- Service: `ArticleService`가 게시글 생성/조회 같은 비즈니스 로직을 수행한다.
- 역할이 분리되어 코드 유지보수와 기능 확장이 용이하다.

## 스프링에서 의존성 주입(DI) 방법 3가지 방법
- 생성자 주입: 생성자를 통해 의존 객체를 주입받는 방식으로, 불변성 보장과 테스트 측면에서 가장 권장된다.
- Setter 주입: setter 메서드로 주입받는 방식으로, 선택 의존성 처리에 유연하다.
- 필드 주입: 필드에 직접 주입하는 방식으로 구현은 간단하지만 테스트/유지보수에 불리하다.
- 현재 프로젝트는 `@RequiredArgsConstructor` 기반 생성자 주입을 사용한다.

## JPA의 장점과 단점
- 장점: 반복적인 SQL 작성 없이 엔티티와 리포지토리 중심으로 CRUD를 빠르게 구현할 수 있다.
- 장점: 객체 중심 설계가 가능해 코드 가독성과 유지보수성이 높다.
- 단점: 영속성 컨텍스트, 지연 로딩 등 내부 동작에 대한 이해가 부족하면 성능 이슈가 발생할 수 있다.
- 현재 프로젝트는 `Article` + `ArticleRepository` 구조로 JPA를 활용하고 있다.

## HTTP GET 요청과 POST 요청의 차이
- GET은 주로 데이터 조회에 사용되며, POST는 데이터 생성/처리에 사용된다.
- GET은 파라미터가 URL에 노출되고, POST는 요청 본문(Body)에 담아 전달한다.
- GET은 멱등성이 보장되지만, POST는 요청에 따라 서버 상태가 변경될 수 있다.
- 현재 프로젝트에서는 목록 조회는 `GET /article/list`, 게시글 등록은 `POST /article/create`를 사용한다.
